# Agent Wiki v0.4 — 编译质量与自进化

> 桃🍑 + Codex 联合规划 | 2026-05-19

## 0. 定位

v0.2-v0.3 解决了"能用"：编译管道跑通、maintain 295s→4.6s、检索 hit_rate 23%→98%。

**v0.4 要解决"好用且自进化"：编译出来的是不是好东西？系统会不会自己变好？**

v0.4 的中心不是新 transport、不是新 adapter，而是三件事：
1. **建立可信 eval 基线** — 先测准"系统现在到底怎样"
2. **建立编译质量门** — 拦住最明显的坏编译
3. **建立可解释的优化闭环** — 先解释，再建议，最后才自治

## 2. 六个核心问题的结论

### Q1: 事实保真度用什么方法？

**结论：证据单元覆盖（Evidence Unit Coverage），不是关键词覆盖**

- 从 raw 侧抽取 evidence units：数字、日期、专有名词、代码标识、配置名、命令、显式因果句
- 从 atom 侧抽取 claim units：句子级 claims + 同类结构化 token
- 三层匹配：
  - **精确匹配**：数字、doc_id、URL、命令、配置键
  - **规范化匹配**：大小写、单复数、连字符、缩写展开
  - **弱语义匹配**：同 raw source_ref 中共享 2+ 关键 token 视为覆盖
- 输出三个子指标：
  - `critical_fact_coverage` — 核心事实覆盖（**Gate 指标**）
  - `named_entity_coverage` — 命名实体覆盖
  - `source_ref_coverage` — 来源引用覆盖（**Gate 指标**）

> 不用关键词覆盖（太粗），不用 NLI（太重）。证据单元是中间方案。

### Q2: n-gram 重合度计算效率？

**结论：O(current_packet_size)，不做全库对比**

- 对比对象：atom content vs 当前 compile packet 的 items[].content_preview
- 可选加：atom summary vs 同 topic 已有 atom summaries
- 复杂度 O(current_packet_size)，不是 O(global_atoms²)

**重要调整：n-gram overlap 不做硬 Gate，只做 warning signal**

- 高质量原子总结可能和原文高度重合（特别是技术笔记）
- 只有"高重合 + 缺少结构化重组 + claim 数极少"组合出现时，才判为失败
- 避免误伤"压缩型好内容"

### Q3: 归因引擎是否需要 LLM？

**结论：v0.4 不需要，纯规则决策树**

- 当前问题是缺少稳定、可回放、可解释的操作诊断
- LLM 归因会把"观察"和"解释"耦合，调参时难做回归对比
- 现有数据源已够做 deterministic decision tree：query_outcomes、review_queue、compile telemetry、eval_history、metadata_completeness、cluster_coverage
- v0.5+ 再考虑"LLM 生成诊断摘要"，但不是"LLM 决定诊断结论"

### Q4: 自动调参的安全性边界？

**绝对不能自动调的参数**（改变 authority semantics）：
- prompt 主体和 schema contract
- page taxonomy / gate policy
- purpose.md 对齐逻辑
- compile create-vs-revise 策略
- source_ref 校验策略
- permissions / max_gate / allowed_page_types
- pending inclusion 默认策略
- review_status / contested 语义

**可以自动调**（窄范围、单变量、可回滚）：
- query ranking boost 数值
- compile suggestion batch size
- relation candidate 阈值
- maintenance 每轮处理上限
- 重试延迟、并发上限

**三约束**：一次只改一个参数 + 步长固定且小 + 没 eval 基线不允许调

### Q5: 编译策略三级切换条件？

**结论：compile_priority_score 多信号打分**

| 信号 | 权重方向 |
|------|----------|
| raw_count | 多→升级 |
| query_hit_frequency | 高→升级 |
| query_miss_frequency | 高→升级 |
| purpose_alignment | 高→升级 |
| existing_compiled_count | 已多→维持 |
| previous_quality_gate_failures | 多→升级（需要重编译） |
| staleness_days | 久→升级 |
| contradiction_markers_present | 有→升级 |

策略分配：
- **Light**：raw 少、查询少、非 purpose 核心、只需最小可检索性
- **Standard**：默认层
- **Deep**：purpose 核心 + 高频被问 + 质量不稳或存在冲突 → 多轮有条件重试

> Deep 不是"更多 token"，而是"多轮有条件重编译"，只对高价值 cluster 开。

### Q6: eval 扩展到其他维度？

**结论：v0.4 分两类，不全做**

**Retrieval eval**：
- strict_recall@5
- loose_recall@5
- must_not_violation@5
- MRR
- compiled_hit_ratio（命中 atom 而非 raw 的比例）

**Compile quality eval**：
- metadata_completeness
- source_ref_coverage
- section_structure_compliance
- quality_gate_pass_rate
- post_compile_query_uplift（**Codex 补充的关键指标**）

连通性、知识图质量、跨域洞察 → 后续 phase

## 3. 技术实现要点（Codex 贡献）

### 3.1 质量门挂载位置

**最安全位置**：`compile_execute.apply_generated()` → **quality gate** → `compile_update.apply()`

- 不把内容质量校验塞进 compile_update（共享写服务，不应知道 LLM 产物结构）
- compile_update 继续只做权限、source_refs、传播一致性
- 质量逻辑只在 compile_execute 边界

### 3.2 review_queue 状态模型扩展

当前 `review_queue.py:142` 只有 resolved/failed。v0.4 需区分：

| content_state | 含义 |
|---------------|------|
| generation_failed | LLM 没返回有效 JSON |
| invalid_output | JSON 结构不合规 |
| quality_rejected | 质量门不通过 |
| quality_warning_committed | 质量门 warning 但已写入 |
| transport_retry | 网络/服务重试 |

### 3.3 参数治理两层架构

不把运行时参数塞进 registry.yaml（会混淆"声明式 wiki 配置"和"运行时优化参数"）：

| 层 | 文件 | 内容 |
|----|------|------|
| 稳定声明式 | registry.yaml | wiki config、权限、compile.llm、dream_cycle |
| 动态运行时 | .agent-wiki/runtime_tuning.json | boost 数值、batch limit、阈值 |
| 变更历史 | .agent-wiki/param_history.jsonl | 每次变更：前值、后值、触发原因、期望效果 |

### 3.4 maintain 职责拆分

maintain 不应变成自治控制器。拆成：
- **metrics_collector** — 采集指标
- **diagnosis_service** — 规则归因
- **tuning_service** — 参数建议/调参
- **maintain** — 只编排调用

### 3.5 质量信息入 manifest

质量信息不能只停留在 review_queue，后续 query/ranking 需要利用。manifest 至少增加：
- quality_status
- quality_score_summary
- quality_checked_at

## 5. 实施分 Phase

### Phase A: Eval 与观测基线（1-2周）

**目标**：先把"系统现在到底怎样"测准

| 任务 | 说明 |
|------|------|
| eval 指标完善 | strict_recall@5、loose_recall@5、must_not_violation@5、compiled_hit_ratio |
| eval_history.jsonl | 每次评估结果写入，含时间戳、参数快照、指标值 |
| quality_report 扩展 | 增加 compile 质量维度：字段完整率、结构合规率、source_ref_coverage |
| query_outcomes 与 eval 分离 | 日常采样 ≠ eval 基准，数据区分展示 |
| maintain 后自动跑 eval | 每次 maintain 完成触发 eval，结果入 history |

**交付标准**：
- eval 可一键运行，单次 <30s
- quality_report 包含 compile 和 retrieval 两个维度
- eval_history 有至少 3 次基线记录

### Phase B: Compile Quality Gate v1（2-3周）

**目标**：拦住最明显的坏编译

| 任务 | 说明 |
|------|------|
| Gate 1: 字段完整性 | summary/confidence/content 非空检查 |
| Gate 2: 结构合规 | content 包含 Claims + Evidence section |
| Gate 3: 证据覆盖 | critical_fact_coverage + source_ref_coverage |
| Gate 4: 信息增量 | n-gram overlap 作为 warning signal（非硬 gate） |
| review_queue 状态扩展 | 区分 generation_failed/invalid_output/quality_rejected/quality_warning_committed |
| compile_prepare 增强 | token budget 动态分配、同 topic atom summary 注入、evidence-unit 抽取 |
| 质量信息入 manifest | quality_status/quality_score_summary/quality_checked_at |
| 失败重试分级 | transport_retry → output_repair_retry → quality_rewrite_retry → human_review |

**挂载位置**：compile_execute.apply_generated() → quality gate → compile_update.apply()

**交付标准**：
- 质量门通过率 ≥85%
- atom 字段完整率 75% → 95%+
- review_queue 能区分 5 种 failure type

### Phase C: Diagnosis And Recommendation（2-3周）

**目标**：先给出"为什么变差、建议调什么"，但不自动执行

| 任务 | 说明 |
|------|------|
| 参数 registry 化 | 硬编码 boost → 统一 config object |
| 参数两层架构 | registry.yaml（稳定） + runtime_tuning.json（动态） |
| 规则归因引擎 | deterministic decision tree，基于 eval_history/query_outcomes/review_queue |
| 诊断输出 | "为什么下降" + "推荐改什么参数" |
| param_history.jsonl | 每次变更记录：前值、后值、触发原因 |
| 基线冻结 | frozen baseline 参数集，用于回归对比 |
| 手动标注闭环 | 复用 feedback + accepted/rejected doc_ids |
| 重复 atom 检测 | summary-level near-duplicate + 同 cluster overlap warning |

**交付标准**：
- 归因引擎覆盖 3+ 诊断路径
- 参数变更可追溯、可回滚
- 重复 atom 检测假阳性率 <10%

### Phase D: Controlled Automation（3-4周）

**目标**：只对低风险参数开小范围自动优化

| 任务 | 说明 |
|------|------|
| 单变量自动调参 | ranking boost、batch limit、relation threshold |
| 自动回滚 | eval recall 下降 >2% → 自动回滚 |
| 编译策略分层 | Light/Standard/Deep，基于 compile_priority_score |
| Deep 编译 | 多轮有条件重试，只对高价值 cluster |
| 价值指标闭环 | post_compile_query_uplift + 知识被引用率 |
| staleness 治理 | 热点但过时 → 触发重新摄入 |

**交付标准**：
- 自动调参不破坏 eval baseline（自动回滚生效）
- Deep 编译质量门通过率 >90%
- post_compile_query_uplift 可度量

| 优先级 | 内容 | Phase |
|--------|------|-------|
| **P0** | Eval 基线 + Compile Quality Gate | A + B |

| **P4** | Deep compile + 价值闭环 | D |

**原则**：先测准，再拦坏，再解释，最后自治。

## 8. 核心设计原则（两人共识）

1. **质量门挂 compile_execute 边界，不污染 compile_update 共享写服务**
2. **n-gram overlap 只做 warning，不做硬 gate** — 避免误伤压缩型好内容
3. **归因先纯规则，不用 LLM** — 稳定、可回放、可解释
4. **参数治理两层：声明式 vs 运行时** — 不混淆 registry.yaml 的定位
5. **maintain 只编排，不当自治控制器** — 拆 metrics/diagnosis/tuning
6. **先测准再自治** — 没有 eval baseline 就不允许调参
7. **自动调参三约束**：单变量 + 小步长 + 有 eval 才调
8. **Deep 编译 = 多轮有条件重试，不是更多 token**
9. **编译后价值验证** — 不只看编译内容本身，看它有没有让 query 变好
